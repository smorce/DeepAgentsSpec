### 私がやりたいこと

- Agent Harness とは複雑で信頼性の高いソフトウェアを大規模に構築・維持する目標を達成するのに役立つ環境、フィードバックループ、これらが制御されたシステムのこと。噛み砕くとAIエージェント（特にLLM＝大規模言語モデル）を長時間・複雑なタスクで「ちゃんと動かせるようにする土台・インフラ」のこと。
- 「ハーネスエンジニアリング」= エージェントが正しく動ける環境（ハーネス）を設計すること。メモリ管理、失敗からの復帰、自己修正、システムプロンプト、ツール選定、実行フローやミドルウェア（モデル呼び出し前後のフック）などを設計し、性能、トークン効率、レイテンシを最適化する考え方。世界中でリアルタイムで研究が進んでいる分野です。
- ゴール：このコードベースは既にハーネスエンジニアリングが実装されていますが、まだ成長途中です。エージェント自身でコードベースであるハーネルを自律的に成長させていくことがゴールです。つまり、私の介入なしに、ハーネスエンジニアリングの改良を自動化すること。月に3つくらいアップデートされるのが理想です。ハーネスエンジニアリングの改良に関係ないアップデートは入れないこと。

AIが勘違いしたっぽくて、現状のリポジトリは私のやりたいことを履き違えています。
例えば、mutations/mutation_exp_083.py などは、基本的に タグ付与・ポリシー付与の純関数ですが、やりたことと全然違います。
現行の運用思想・検証フローは「SoR周りの自律改善」が主で、ディレクトリ構造の全面変更を前提にしていませんが、これもやりたことと全然違います。

### 原則

- レポジトリ自体を“知識のシステム・オブ・レコード”にすること。

### この仕組みが何を目指しているか

この構造は、「AIエージェントによる自律的なシステムの改善サイクル」を管理するためのものです。

1.  Radar (監視): `monitoring_targets.json` などに基づき、システムの課題や改善点を見つける。
2.  Backlog (計画): `experiment_backlog.json` に改善案を溜める。
3.  Mutation (実行): `mutations/` のスクリプトを生成・実行してコードを修正する。
4.  Implemented (記録): 成功した変更を `implemented/` に永続化し、履歴として残す。

つまり、`mutations` は「エージェントがこれから打つ手」であり、`implemented` は「エージェントが過去に打った手の記録」であると言えます。

### 指示

ハーネスエンジニアリングの改良を自動化することを目的に、

- Radar (監視): monitoring_targets.json などに基づき、システムの課題や改善点を見つける。
モニタリングだけでは課題に気付けないと思うので、以下の観点でも積極的に改善点を出したいです。
→**公式ブログの最新記事の「本文」を読んで**、これまで蓄積してきたナレッジの中にはない新しいアイデアもしくはシステムには取り入れられていないアイデアがあるかを評価する → 現在のコードベースを分析し、そのアイデアをシステムに取り入れることによる効果とリスクを分析する(（現状→理想→差分）” をSoR化) →  → デメリットよりもメリットが大きい良いアイデアであれば、システムの課題や改善点を洗い出す。
公式ブログの最新記事を読んだだけでは情報不足の場合は Zenn,Qiita,note などにも解説記事が上がってないか積極的に情報収集して活用してください。
また、捨てたアイデアも理由ありで記録しておきたいです。
現在の update がやっていることと違うかもしれませんが、「差分検出」とはこういう分析のことを指します。

Backlog (計画): experiment_backlog.json に改善案を溜める。
→作成した計画はレビューを挟みたいです。何度もエージェントによるブラッシュアップをさせて計画を洗練させるフェーズを追加したいです。洗練がOKの判断も自律的にさせたいので、判断評価軸も持っておきたいです。1回のセッションでレビューループを回してOKまで改善させるのか、それともセッションをまたいで毎回コンテキストをリセットした上でレビューさせ、OKが出るまでそのループを回すのかだと、後者にしてください。ここの設計を具体化してください。
できれば、CodexCLI (codex 5.1 mini) の非対話モードをFor文で回して、レビューステータスがコンプリートになるまで毎回新しいセッションでレビューしていく、レビューコメントや判断結果も毎回同じファイルに追記していく(セッションIDで共通のファイル名にする)。プロンプトは考えてください。例えば、「あなたはレビュー担当のエージェントです、レビュー内容はXXX、評価観点はXXX、アウトプットはXXXです、過去のメモはXXXXです。」みたいなプロンプトです。レビューエージェント以外に必要なエージェントは全部用意してください。

Mutation (実行): mutations/ のスクリプトを生成・実行してコードを修正する。
→現在の拡張範囲を教えて下さい。どの程度改善されるのか？ 例えばコードベースのディレクトリー構造から大胆に変更される可能性があるのか？ もしくはもっと小規模な改善に留まるのか？
大規模な改修をした方がいい場合はしっかり計画を練ってから人間の承認を待たずに実行してください。ディレクトリ構造を変更する場合もSoR化したくて、まずマークダウンのリスト形式（インデントされた構造）を作成し、それから実際のディレクトリとファイルを生成するスクリプトを生成して、そのスクリプトを実行する形式にしてください。

常にロールバックできるように、常にコミットメッセージは包括的なメッセージにしてください。
意味が分からなければ質問してください。
